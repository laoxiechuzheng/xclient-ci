# Native desktop update QA (CI only)

The explicit `macos_confirmation=confirm-owned` control accepts either existing Mac signer enum:shipping `adhoc` or the `ephemeral-self-signed` comparison. Both require the fresh hosted Mac fixture,owned disposable data Keychain and nonce item,existing Accessibility permission,verified Apple SecurityAgent/owned V2 identity and the unique matching system dialog. Default confirmation is disabled. No original login password or permission request is permitted.

Same-certificate/owned-data-Keychain control41819500600 proved item placement and all original update/value/exit/cleanup gates,but observed no system confirmation and stayed red. Shipping ad-hoc is a distinct identity condition;whether a natural matching prompt appears is an unproven hypothesis. No ACL edit,manual lock or dialog manufacture is part of it. A run without the required observed action still fails;original-login and unattended compatibility remain unproven. Ad-hoc creates no certificate-signing Keychain;the separate owned data-Keychain cleanup is mandatory.

This fixture tests a real `1.0.0-pre.1+10000401` to `1.0.0-pre.2+10000402` update in a fresh GitHub-hosted Windows/macOS VM. It uses a separately compiled example `SAFE_MODE` entry, normal application bootstrap, real `XcUpdateManager`/HTTPS/signature/hash checks and the production installer. App exit uses `SystemAction.handleExit`; the driver records app/Core/helper PID, executable and start identity and never kills by name. No existing workflow is changed here.

The driver imports the frozen CI helpers from `native_store_smoke.py`: `ci_identity`, `scoped`, `process_identity`, `network_hash`, `write_new`, `require`, plus generated-config/define verification. It does not invoke the store QA target or its prepare/run commands. Existing Flutter/Go/Rust/Inno/OpenSSL/Python tools are required; no tool or package is installed by the driver.

Only `prepare`, `brand`, `stage` and `run` on a matching GitHub-hosted runner are accepted. A new `out/` directory, fresh nonce, current job/SHA, current QA source hashes, generated Flutter target/defines, fresh Dart payload and distinct v1/v2 binaries are checked. The Windows Inno AppId/mutex/process names must be example-specific. `brand` validates and freezes the actual `make_config.yaml`, source `inno_setup.iss`, pubspec, distributor options and runner mutex inputs. `stage` requires their exact byte hashes to remain unchanged after packaging. The pinned distributor deletes its generated temporary `.iss` after a successful ISCC run, so no generated-script file is required or substituted. The installer and example service/registration/processes must not already exist. The job must never run these commands on a user workstation or self-hosted runner.

## Windows job

Reuse the existing `windows-2022` release toolchain, CA preparation, submodule setup and `flutter pub get`; both native build hooks stay enabled. Activate the same distributor version used by `setup.dart` if it is not already available:

```powershell
dart pub global activate -s git https://github.com/chen08209/flutter_distributor.git --git-ref v0.6.11-flclash.4 --git-path packages/flutter_distributor
$out = "$env:GITHUB_WORKSPACE/out/native-update-windows"
$state = "$out/private/state.json"
python tool/xclient/ci/native_update_smoke.py prepare --platform windows --output $out
foreach ($stage in @('1', '2')) {
  python tool/xclient/ci/native_update_smoke.py brand --platform windows --state $state --stage $stage
  if ($LASTEXITCODE -ne 0) { throw 'QA brand preparation failed' }
  flutter_distributor package --skip-clean --platform windows --targets exe --description amd64 --build-target=test/xboard/native/update_app.dart "--flutter-build-args=dart-define-from-file=$out/private/v$stage-defines.json"
  if ($LASTEXITCODE -ne 0) { throw 'QA Inno build failed' }
  $packages = @(Get-ChildItem -LiteralPath dist -Recurse -File -Filter '*.exe')
  if ($packages.Count -ne 1) { throw 'One new Inno package required' }
  python tool/xclient/ci/native_update_smoke.py stage --platform windows --state $state --stage $stage --bundle build/windows/x64/runner/Release --package $packages[0].FullName
  if ($LASTEXITCODE -ne 0) { throw 'QA Inno staging failed' }
  Move-Item -LiteralPath dist -Destination "$out/private/dist-v$stage"
}
python tool/xclient/ci/native_update_smoke.py run --platform windows --state $state
if ($LASTEXITCODE -ne 0) { throw 'Native Windows update QA failed' }
```

The first actual Inno package installs silently with `/DIR` pointing to this job's new private directory, no icons/tasks and no automatic app launch (`skipifsilent`). The installed v1 then downloads the signed v2 package and invokes the real detached PowerShell updater. That updater intentionally has no `/DIR`: the test checks that the same AppId reuses the initial installation directory. After both the initial installation and update, the actual GUID uninstall registry entry must exist, resolve to this job's installed directory and have `DisplayVersion` exactly equal to the corresponding complete pubspec version, including `+build`. Expected bundle bytes are checked separately. The real helper relaunches v2; a manually copied portable v1 is not substituted for the first installation.

Inno itself still calls its existing stale-proxy cleanup and helper-service uninstall code. `SAFE_MODE` does not remove those installer operations. This is why a new VM, absent example service/registration/processes and unchanged proxy/interface hashes are mandatory. Cleanup uses only the uninstaller inside this job's installation and checks the example registration/service are gone. GitHub Windows VMs run as administrators with UAC disabled: success does not verify interactive UAC acceptance/refusal or standard-user elevation.

## macOS job

Reuse the existing `macos-15` toolchain, dependencies and native CA preparation. The minimal fixture builds and runs the host architecture; it does not claim an Intel execution or a shipping universal build. The private zip uses the production manifest asset key/name to exercise the real selection/installer path and must never be published as a distribution artifact.

```bash
set -euo pipefail
out="$GITHUB_WORKSPACE/out/native-update-macos"
state="$out/private/state.json"
python3 tool/xclient/ci/native_update_smoke.py prepare --platform macos --output "$out"
plutil -replace FLTEnableImpeller -bool NO macos/Runner/Info.plist
for stage in 1 2; do
  python3 tool/xclient/ci/native_update_smoke.py brand --platform macos --state "$state" --stage "$stage"
  flutter build macos --release --target=test/xboard/native/update_app.dart \
    --dart-define-from-file="$out/private/v$stage-defines.json"
  python3 tool/xclient/ci/native_update_smoke.py stage --platform macos --state "$state" --stage "$stage" \
    --bundle build/macos/Build/Products/Release/ExampleClient.app
done
python3 tool/xclient/ci/native_update_smoke.py run --platform macos --state "$state"
```

Staging uses the same release entitlements/ad-hoc codesign and `ditto` zip commands as shipping. The driver first installs v1 by copying its real bundle to the job's directory. The production installer unpacks, validates and swaps the bundle; its actual detached shell and `open` must produce a new v2 PID at that exact path. The driver does not perform the update copy or launch v2 on its behalf. It verifies every expected bundle file against the staged v2 and requires distinct CDHash values. An extra Intel job or actual universal slices may later reuse this protocol; the host-only receipt must remain explicit until then.

## Facts, storage and process ownership

`prepare` creates fresh ctrl/rel keys, a localhost certificate and a temporary example brand under `private/`. Only the QA process explicitly trusts that certificate; no CA is installed in the OS. `run` signs the policy and release facts using seeds passed only in signing subprocess environments, then deletes both seeds. A standard-library HTTPS server exposes only an exact allowlist of the policy, release facts and actual packages. It binds only loopback; an occupied prepared port fails rather than changing compiled endpoints.

The v1 QA entry requires the live GitHub-hosted job environment. Both stages require the compiled nonce/config hash, owned marker, exact installed executable and a fresh driver lease naming the actual PID and binary hash. v2's lease works after the real launcher/`open` restart without requiring test command-line arguments or assuming inherited shell environment. No stage performs installation until its controller lease and normal bootstrap succeed.

v1 writes a synthetic value to a nonce-derived `PlatformSecureStore` namespace only after confirming the key is absent without a native read error. v2 must read, replace and delete that same key across the real update. Read errors swallowed by the production wrapper are detected from its safe log sink, including the `[xclient]` prefix. No existing credential, permission dialog, Keychain ACL or OS security policy is changed. Keychain access denial, timeout or an unconfirmed synthetic-key cleanup fails the test; the driver never deletes an entire credential store. macOS ad-hoc identities change between binaries, so a cross-version ACL prompt is a meaningful failure requiring review, not a dialog for automation to accept.

Both stages request the real application exit coordinator. On desktop its successful path terminates the process with `exit(0)`; an exception or unexpected return revokes the stage's request receipt, writes a fixed failure receipt and exits nonzero. The driver checks both request receipts, all recorded processes gone, no failure receipt and the actual v1 child exit code equal to zero. It rechecks for failures after cleanup before deciding success. `exit_observed_after_production_request` describes that evidence; it does not invent a v2 exit code for a process launched by the helper/`open` rather than Python. The driver also observes verified parent/child chains and the exact nonce-scoped, hash-checked Windows download executable, so active update Inno descendants are included in failure containment. It never adopts a process merely because its name matches. Identity-checked termination cannot turn an unconfirmed normal exit into success. Initial-install/uninstaller subprocess timeout can still leave an unobserved OS descendant: that is a red, cleanup-unconfirmed run contained by the disposable VM, not proof every failure subtree was recovered. App bootstrap may create example preferences/cache in the ephemeral VM; the fixture does not broadly scrub application-data or Keychain directories. The VM is disposed by GitHub after the job.

## Evidence and limitations

### Cross-version Keychain diagnosis

The actual macOS run after the bounded observer fix reached the production swap and a new v2 PID, then failed at the broad secureStore checkpoint with a timeout and unconfirmed synthetic-item cleanup. That is not a storage pass. The QA target now instruments each existing operation independently through `update_store_observer.dart`, whose hash is frozen alongside the target and contract in the prepared job state. Production `PlatformSecureStore`, plugin source, options, dependencies and Keychain permissions are unchanged.

`store-<stage>-<id>-begin.json`, `-end.json` and `-nativeReturn.json` contain only bounded operation ids, fixed operation/event/outcome enums, start/elapsed milliseconds and optional native-method/late/error categories. A QA-only `FlutterSecureStorage` subclass forwards all original arguments to the same superclass methods. For a native `PlatformException`, only a signed 32-bit integer `details` value is recorded as OSStatus; error code is reduced to securityStatus/missingParameter/unknown and the message is never emitted. Key, service, account, value and option maps are not recorded. Existing 15-second waits, synthetic comparisons, swallowed-read detection and cleanup requirements stay intact. Operation ownership is bound in the async zone before the call, so a native completion after its Dart timeout remains associated with that original id and cannot turn the failed end receipt into success or become the subsequent cleanup operation.

The locked Darwin plugin uses one serial queue and synchronous Security API calls. A timed-out Dart future does not cancel a pending native call; a later cleanup delete may wait behind it. The new operation receipts identify this boundary but cannot establish an authorization prompt without native evidence. Apple's [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) describes ad-hoc identities as version-specific, while [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html) describes default Keychain identity tracking through the creator's designated requirement. These support an investigation, not an automatic attribution of the current timeout.

macOS staging now reads actual v1/v2 designated requirements using `codesign --display -r -`. Raw requirements remain in the job's private directory. `signing-1.json`, `signing-2.json` and `signing-compatibility.json` expose only hashes, fixed requirement forms, ad-hoc/CDHash metadata and self/cross-verification booleans. Verification rechecks the private file's hash/regular-file/size constraints, reads its single requirement and passes `-R` plus `=` followed by that expression as separate argv elements. The explicit literal form avoids file-format auto-detection; no shell interpretation or raw requirement logging occurs. Apple TN3127 also documents text-file input, but this fixture uses the explicit literal form. No re-signing with another identity, certificate import, Keychain item query or ACL modification occurs. Unavailable/failed diagnostics remain explicitly unknown and cannot substitute for the storage test.

Apple TN2206 also shows an implicit requirement as the exact line `# designated => ...`. The extractor now accepts either one plain `designated => ` line (`source=explicit`) or one line with the single exact `# ` prefix (`source=implicit`). It does not strip arbitrary comments or accept multiple `#` characters. Multiple or mixed designated markers remain unknown, including a malformed marker alongside a valid one. Hashes cover only the original requirement expression, never its display prefix. The earlier macOS signing receipts reported missingRequirement and did not upload the raw display, so the old parser's inability to recognize this documented form is verified, while the precise original runner text cannot be reconstructed from those receipts alone.

When an owned v2 operation is still pending after five seconds, the driver may attempt at most two native-display captures, at least five seconds apart. It first verifies the live App's complete identity and calls only `CGPreflightScreenCaptureAccess`. If capture is not already permitted, it records permissionUnavailable without requesting permission or interacting with a dialog. Otherwise built-in `screencapture -x -t png` writes privately with a five-second deadline. Only a fresh, bounded PNG with valid header/IHDR/IEND checks and an unchanged owned App identity is copied into `receipts/`; invalid/partial captures stay private. This runs solely on the already-guarded fresh GitHub Mac, containing no production login or opened private-key documents. A native alert may show the synthetic item label. There is no click, focus, typing, dismissal, authorization or workstation screenshot.

### Disposable self-signed control

The manual workflow also accepts `macos_signing=ephemeral-self-signed`; `adhoc` remains the default and Windows rejects the certificate mode. `prepare` binds the explicit mode and signer-helper source hash. Before building either App, `signing-preflight` creates one one-day codeSigning certificate/key in the owned private output and one isolated signing Keychain. Import trusts only `/usr/bin/codesign`; the necessary `apple:` partition applies only to this newly imported key. No global trust or login/data-item ACL changes occur. Existing default/login Keychains must exist. Their identities and ordered search list are restored and checked before App operations; signing always names the owned Keychain explicitly.

The cheap preflight signs two different miniature binaries with that same certificate. Actual embedded-leaf fingerprints, both self checks and both cross-DR checks must pass; a strictly valid ad-hoc binary with the same identifier must fail the certificate DR. Only then may normal SAFE v1/v2 builds proceed. Each staged bundle must embed the same certificate, pass strict verification and both actual cross-DR checks. The product installer and storage tests remain unchanged, including the normal certificate-identity branch, every synthetic value comparison, original timeout, exit and cleanup requirements. This control starts both versions certificate-signed and grants no ad-hoc-to-certificate migration exception.

`signing-cleanup --platform macos --state <owned-state>` is an always step before receipt upload, including preflight/build failures. The run also calls it in its own `finally`. Cleanup removes only owned signing files/Keychain and verifies the original Keychain state; an external state change is refused instead of overwritten. A failed cleanup keeps the job red. Only finite receipts and approved diagnostic PNGs are artifacts; no private key, password, import container, raw requirement or test-signed package is uploaded. This disposable identity is destroyed and cannot sign future customer updates. Persistent signing identity, backups and new CI secrets remain separate delivery work. These are implemented test gates, not a claim that actual Mac cross-version storage already passes.

Actual preflight `41802843172` isolated `security login-keychain -d user` returning1 before identity generation,with cleanup passing. Apple's [SecurityTool implementation](https://github.com/apple-oss-distributions/Security/blob/main/SecurityTool/macOS/keychain_list.c) compiles the domain-specific login query out and returns failure there,although the command summary advertises `-d`. The fixture now uses the implemented undomained `login-keychain` read;default/search-list queries retain their explicit user domain. This changes a read-only query,without inventing a missing Keychain or altering its preferences. A regression reproduced the old argv failure before the correction;actual preflight must still confirm the result.

The supported query subsequently passed and a disposable identity imported successfully. Run41804479729 isolated the next failure to `codesign --sign`,with only the fixed-vocabulary message indicating that the requested item could not be found in the Keychain;cleanup still passed. GitHub's [official signing setup](https://docs.github.com/en/actions/how-tos/deploy/deploy-to-third-party-platforms/sign-xcode-applications) explicitly lists the temporary signing Keychain. The fixture now adds only its owned Keychain to the original ordered search list while signing,then restores the exact original state in `finally`,including sign failures. Default/login Keychains and trust settings are untouched. A root regression proves the temporary list precedes codesign and restoration still runs on error. The next preflight records whether the owned Keychain was initially listed;this is a controlled diagnosis,not yet proof of a successful cross-version App update.

`native-store-pending-1.json` / `-2.json` describe the bounded capture attempts, operation id, fixed reason and optional PNG hash/size; successful images use corresponding `.png` names. Root must inspect those actual native PNGs. A Flutter-engine image cannot show SecurityAgent dialogs, and a missing image or permission does not prove that no prompt appeared. Capturing a prompt or incompatible DRs is diagnostic evidence only: all original native installation, signed update, cross-version read/replace/delete, process exit and cleanup gates remain necessary.

### Process lifetime diagnosis

The first actual macOS run after the certificate correction reached verified download, the real helper and the v1 production-exit request, then failed ownership validation before v2 was observed. That driver retained a direct `Popen` for v1 and did not wait for it until after the v2 hello. The production swap script meanwhile uses `kill -0` to wait for that PID to disappear. The subsequent real `/bin/cat` probe confirmed the lifetime mechanism on macOS: the live full identity matched; after stdin EOF the unreaped child became Z with the same start time, but its reported executable changed and the original observer correctly refused it; after `Popen.wait`, normal exit status was zero and the PID disappeared. This supports the controller dependency problem rather than an exception for accepting changed identities.

The macOS update controller now initializes its direct v1 child to `None` and nonblockingly polls only that actual `Popen` before each process scan. `Popen.poll` reaps an exited direct child without sending a signal; it does not authenticate or reap arbitrary observed PIDs. Windows scanning is unchanged. The full recorded PID/executable/start identity, child-adoption and signal gates remain strict, including PID reuse after that poll. No zombie, basename or changed-start exception has been introduced. Short-lived indirect children such as `ditto` still use the original gates; the next full macOS update run must determine whether another boundary remains.

The next actual update run still failed with an untyped fixture error; its final cleanup observed the direct v1 PID as Z, but that does not identify the original error. A direct child can exit between the pre-scan poll and a later `ps` query. Owner observations now preserve the owned PID, fixed phase and underlying exception kind internally. A macOS scan may retry once only when that failure is attributed to the actual direct v1 `Popen`, with either unchanged recorded PID/start or a process-disappearance query failure; the controller must then nonblockingly reap that child and confirm its PID is absent before rerunning the unchanged strict scan. A different owner, changed PID/start, unrelated query error, still-live/reused PID or any second scan failure remains red. No state or basename classification authorizes this retry or any signal.

`runner-result.json` now records fixed `checkpoint` and `exception_kind` fields, plus separate `process_observation` and `cleanup_process_observation` metadata. These report only the actual direct-child PID/return status, finite failure phase/kind and bounded-retry booleans. `cleanup_exception_kind` is separate from the primary failure; final cleanup cannot overwrite its cause. Raw exception strings, commands and output are not added. Existing success booleans, both exit requests, actual v1 exit code zero and all recorded owners gone remain mandatory. Controlled offline tests cover exit after the first poll, strict rescan after the direct child is reaped, one-retry bounds and rejection of live changes/reuse/other owners; matching actual macOS update evidence remains required.

On a macOS mismatch, `ownership.json` now records only its fixed observation/cleanup phase, owned PID, exact-field match booleans, a fixed executable-path class, and an additional `ps` snapshot reduced to state, parent PID and start/path-class comparisons. It never exports raw command output or arguments. This extra snapshot is diagnostic only and is not used to authorize a process or signal. Diagnostic collection failure leaves the original ownership refusal intact.

A separate no-App diagnostic can run in the lightweight GitHub-hosted macOS SDK job without either native build:

```bash
python3 tool/xclient/ci/native_update_smoke.py process-probe --platform macos \
  --output "$GITHUB_WORKSPACE/out/native-process-macos"
```

It first applies the same CI/platform/output guards, then starts only `/bin/cat` with no arguments as Python's single direct child, blocked on its own stdin. Apple's [cat manual](https://raw.githubusercontent.com/apple-oss-distributions/text_cmds/main/cat/cat.1) and [implementation](https://raw.githubusercontent.com/apple-oss-distributions/text_cmds/main/cat/cat.c) specify reading stdin when no file is supplied, until EOF. The parent never writes input, sends output to `/dev/null` and checks the image against the resolved fixed `/bin/cat` path. Before that admission check can reject the child, `probe-result.json.child_identity` records only its PID, PID/image match booleans, nonempty-start boolean, fixed path classes and finite `ps` snapshot. Unexpected raw image paths are not uploaded.

After checking the live full identity, the probe closes stdin to permit natural exit, observes `ps` and runs the unchanged strict observer before calling `Popen.wait`. Finally it reaps that direct child with a bounded wait, verifies that its PID is absent and checks source/network hashes. No App, installer, socket listener, proxy or TUN is started. The observation code follows Apple's documented [ps state fields](https://raw.githubusercontent.com/apple-oss-distributions/adv_cmds/main/ps/ps.1); the direct child wait follows Python's [Popen implementation](https://raw.githubusercontent.com/python/cpython/3.11/Lib/subprocess.py). The first probe used the current Python launcher but was rejected at its initial executable-path check before observing an exit. That run did not establish a zombie or the actual update failure's cause; switching to the fixed OS binary avoids conflating launcher aliases with the lifetime experiment while preserving the image gate.

Upload only `out/native-process-macos/receipts/` as its own artifact. `probe-result.json` describes whether the diagnostic itself ran and cleaned up, including independent `zombie_observed` and `observer_refused_before_reap` booleans; `ownership.json` contains the bounded mismatch details. The revised probe preserves that original pre-reap observation, then uses the same direct-child scan/reap path and requires `direct_child_reaped_before_scan` plus `observer_passed_after_reap` for its follow-up control, with finite `process_observation` metadata. A successful diagnostic does not require a particular pre-reap hypothesis to be true and does not establish native-update acceptance. Actual macOS results for this revised follow-up control and the controller fix still require fresh matching CI runs; offline tests alone do not prove the complete native update.

Upload **only `out/native-update-*/receipts/`**. Never upload the parent directory or `private/`: those contain fixture seed/key/certificate/config/defines/packages and local installation logs. Receipts contain only job-owned process identities, hashes, booleans, raw OS package version/build fields and fixed error classes; no account, token, storage key/value or IPC arguments are recorded. OS-normalized version fields are recorded alongside the checked canonical ClientInfo pair rather than used to infer it. Successful `runner-result.json` requires actual first installation, forced signed update handoff, v1 exit, native v2 identity, v2 file hashes, storage continuity/deletion, normal process exit, installation cleanup and unchanged network hashes.

If the production manager returns before the native handoff, the run still fails. `failure.json.update` captures the manager state before cleanup: its phase, an allowlisted error code (unknown codes become `unknown`), force flag, received/total byte counts and whether a verified release manifest was obtained. A fixed `checkpoint` also distinguishes policy fetch/verification, manager execution, helper spawn/identity and exit. `exception_kind` is classified by a fixed set of exception types; helper exceptions retain that classification even when the manager catches them. Unknown exception types become `unknown`. These fields exclude error details, display messages, URLs, headers and manifest contents. Forced `onPolicy` starts an update automatically; a subsequent `start()` joins the same in-flight run rather than reporting completion because it is busy. A controlled-HTTP test exercises that real manager behavior. These diagnostics identify the failed boundary without claiming that the first Windows/macOS failures' hidden causes have been recovered.

This fixture does not prove real-account login, production distribution availability, downloaded-app Gatekeeper first-launch prompts, UAC interaction, TUN/helper operation, Intel execution or a shipping universal artifact. The manager's force flag is observed, but `SAFE_MODE` masks real connection behavior; the existing policy-admission tests remain the evidence for that gate. There is no installer substitution, fallback to a fake success, permission auto-acceptance or skip-to-pass branch. Native success may be recorded only after the actual matching CI run.
