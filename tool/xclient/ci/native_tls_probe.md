# macOS SDK TLS context probe

This CI-only component probe diagnoses the native-update fixture's `policyFetch`/`handshake` failure. It does not build or install an application, alter product TLS behavior, add an OS/Keychain CA, or change a proxy/TUN setting. A successful component run is not native-update acceptance.

Run only on a fresh GitHub-hosted macOS job with the existing Flutter 3.47.6/Dart 3.13.5 SDK, Python/OpenSSL and the already checksum-pinned Mozilla bundle:

```bash
python3 tool/xclient/ci/native_tls_probe.py \
  --output "$GITHUB_WORKSPACE/out/native-tls-macos" \
  --mozilla-ca core/Clash.Meta/component/ca/ca-certificates.crt \
  --mozilla-sha256 "$CA_BUNDLE_SHA256"
```

The launcher applies the existing `ci_identity('macos')` and workspace-output guards before creating a directory or listener. A nonce, current job, source/input SHA-256 values, actual SDK path/version and a fresh private config bind the subprocesses to this run. It invokes only the current SDK's `dart --disable-dart-dev` with the SDK-only probe; no pub get, package dependency, Go/Rust or native App build is involved.

Certificate creation calls the same `generate_fixture_certificate` function as native-update QA. It creates a one-day RSA2048/SHA256 test Root CA with critical CA/pathlen0 and certificate/CRL-signing usage, then signs a separate one-day localhost server leaf with critical CA:false, digitalSignature/keyEncipherment, serverAuth EKU and DNS/IP SANs. Python serves the leaf/root full chain with only the server key; Dart imports only `ca.crt`, never the server leaf. Four independent loopback ports/Python SSL server contexts reuse `HttpsFixture` and that chain. The first Dart process uses one isolate and fresh TLS connections to test default context plus fixture CA trust, then default context after additionally importing Mozilla roots, and an explicit fixture-CA-only context. A separate SDK process imports Mozilla roots without fixture CA trust and must reject the connection with a certificate handshake refusal. Every bad-certificate callback returns false. Each request has bounded connect/read time, each child has a 45-second deadline, and cleanup closes only these child processes/listeners/sockets. Unconfirmed cleanup or changed network hashes keeps the result red.

The first real macOS SDK run rejected all three positive paths, including the explicit context; the old fixture was a CA:true certificate without key usage or serverAuth EKU. That result did not support a Mozilla-import overwrite theory. Apple's documented TLS server requirements include a serverAuth EKU for certificates issued after July 2019; the corrected fixture now supplies a proper server leaf. This is a QA certificate correction, not a change to product trust. Offline structure checks and OpenSSL sslserver/localhost/IP verification do not substitute for rerunning the macOS SDK handshake or the rebuilt native App update. [Apple certificate requirements](https://support.apple.com/en-my/103769).

The corrected fixture's next real SDK run still rejected all three positive connections. The probe therefore also evaluates the same leaf→CA chain directly through the macOS system Security/CoreFoundation APIs via Python `ctypes`: SSL server policy for localhost, fixture-only anchors, anchor-only=true and network-fetch=false. A separate negative evaluation supplies an empty anchor array. It does not add a Keychain item, system CA or trust exception. All created/copied CF objects are released; borrowed error domains are not released. `sec-trust-positive.json` and `sec-trust-negative.json` distinguish API/binding/cleanup failures from actual trust refusal using fixed checkpoints/reasons, OSStatus, CFError code/domain enum and SecTrustResultType. A negative result without a real error reference/code and valid refusal result is unconfirmed and remains red. The original SDK success gates are retained, so native trust success alone cannot make a failing SDK handshake pass. The bindings follow Apple's published [SecTrust](https://raw.githubusercontent.com/apple-oss-distributions/Security/main/trust/headers/SecTrust.h), [SecPolicy](https://raw.githubusercontent.com/apple-oss-distributions/Security/main/trust/headers/SecPolicy.h) and [CoreFoundation ownership](https://raw.githubusercontent.com/apple-oss-distributions/CF/main/CFError.h) declarations.

The actual native evaluations subsequently returned OSStatus-domain error `-67903` in both positive and negative paths. Apple's [SecBase.h](https://raw.githubusercontent.com/apple-oss-distributions/Security/main/base/SecBase.h) defines this as `errSecCertificateDuplicateExtension`; the finite reason is now `duplicateExtension`. A malformed-certificate refusal cannot establish the empty-anchor control: that gate additionally requires `untrustedAnchor`. `extensions.json` now counts the CA and leaf's DER extension OIDs, emits only fixed standard-extension names and numeric counts, and requires uniqueness for both certificates. Unknown OID values, DER and PEM are never emitted. `openssl.json` records only a fixed OpenSSL/LibreSSL/unknown family and three numeric version components.

The next actual macOS run identified OpenSSL 1.1.1, not LibreSSL. Its CA contained six extensions but only four distinct OIDs: basicConstraints and subjectKeyIdentifier each occurred twice, while keyUsage and authorityKeyIdentifier occurred once. The server leaf had six unique extensions. OpenSSL 1.1.1's [req.c](https://raw.githubusercontent.com/openssl/openssl/OpenSSL_1_1_1-stable/apps/req.c) defaults to its host request config, reads `x509_extensions`, then adds that section followed by the separate `-addext` section. This explains the observed CA duplicates when both sources specify basicConstraints and subjectKeyIdentifier. The earlier LibreSSL source comparison was a hypothesis about implementation behavior, not evidence of the runner's tool family.

Certificate generation now supplies the same private `request.cnf` explicitly to both `req` calls. That config defines only noninteractive request/DN settings and one CA extension section, selected once using `-extensions`; there is no `-addext` or implicit `x509_extensions`/`req_extensions` inheritance. The CA has exactly basicConstraints, keyUsage and subjectKeyIdentifier. Server signing retains the separate explicit six-extension file, serverAuth, SANs, strength, validity and SHA256 settings. A real subprocess regression sets `OPENSSL_CONF` to a polluted host config containing overlapping CA extensions, a clientAuth restriction and an unrelated CSR SAN: the old helper imports that restriction and fails, while the corrected helper produces unique CA/leaf OIDs and a clean CSR. Local OpenSSL 3.5.9 replaces overlapping extensions instead of reproducing the runner's duplicates, so that local RED proves configuration leakage; the earlier actual OpenSSL 1.1.1 counts establish the duplicate-OID failure. Actual macOS SecTrust/SDK results still require a fresh run of the corrected helper. No product trust change or OS trust exception is involved.

Upload **only `out/native-tls-macos/receipts/`**. `append.json` and `mozillaOnly.json` record booleans, fixed exception/reason classes, numeric OS error codes, callback counts and subprocess exit/stderr byte counts. They never contain raw exception messages, certificates, PEM, URLs or private keys. `certificate.json` still describes the server leaf: only X509 version, constraints/usage/EKU/SAN booleans and a fixed signature-algorithm enum parsed from OpenSSL's public-certificate description in memory. Unknown certificate properties remain unknown rather than inferred. `inputs.json.certificate_sha256` now hashes the imported CA, with separate leaf/full-chain hashes. Private certificate/key/config files stay under `private/` and must not be uploaded.

SDK bad-certificate callbacks and connected peer certificates now record only whether DER bytes match the hash-guarded `server.crt` and whether the current instant is within the certificate's SDK validity dates. No DER, PEM or date strings leave memory. Successful connections and the no-root refusal must concern the exact fixture leaf with current validity; a different certificate cannot satisfy the controls. `native_tls_probe_test.py` exercises the ctypes call/ownership/error paths with pure fakes and never loads native libraries or opens a listener. These offline tests cannot establish the actual macOS SecTrust result.

The synchronous native `SecTrustEvaluateWithError` call is bounded by the TLS job's 20-minute limit, separately from the 45-second deadline for each Dart child. Network fetching is disabled for that native evaluation.

The fixed-config macOS run41779064447 at0647269 passed all original strict SDK paths: fixture/default trust, appended Mozilla roots and explicit context each connected and read the expected HTTP body with zero bad-certificate callbacks; the separate Mozilla-only process rejected the exact fixture leaf. Native SecTrust accepted the fixture-only anchor and rejected the empty-anchor chain with untrustedAnchor/-67843. CA3/leaf6 extensions were unique; peer DER/current validity, child/server cleanup, inputs and network snapshots all matched. This confirms the certificate-generation cause and the component fix on the actual runner. It does not establish the rebuilt macOS App's installation, update handoff or cross-version storage; those remain separate native-update gates.
