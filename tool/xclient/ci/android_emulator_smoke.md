# Official Android SAFE emulator smoke

This manual-only test installs the actual example-brand x86_64 APK on one fresh Google Android 15/API35 emulator. The workflow's `android_build_mode` selects `debug` (default) or `profile`; both jobs must use that same mode. Debug has the exact package `com.xclient.example.dev` and a JIT kernel payload. Profile has the exact package `com.xclient.example` and an AOT x86_64 `libapp.so`, with no debug kernel. These two identities are fixed allowlisted SAFE examples, not a general package override. C33 authorizes downloading the official emulator and one `system-images;android-35;google_apis;x86_64` image on a disposable GitHub-hosted Linux runner. It does not add an App dependency. The native Android API37 compilation target and shipping minSdk are unchanged; API35 is the first OS runtime acceptance baseline.

The launcher rejects local, self-hosted, non-Linux and non-manual execution before creating an output directory, invoking the SDK/ADB or opening a listener. Set `XCLIENT_ANDROID_QA=official-safe-x86_64-v1` only in the dedicated jobs. Compilation belongs to fixed job `android-apk`; SDK/image installation and emulation belong to fixed dependent job `android-emulator` on a second fresh runner. These roles are enforced in the CLI, so the large compile and image phases cannot accidentally recombine in one job. The producer uses the existing pinned Flutter3.47.6/Dart3.13.5, Go1.27.1, Java17, NDKr28c, checksum-pinned CA preparation, locked dependencies and example brand application. Both native build hooks remain true.

Both jobs retain the established cleanup of the four unused preinstalled tool directories `/usr/share/dotnet`, `/opt/hostedtoolcache/CodeQL`, `/usr/local/.ghcup` and `/opt/ghc` after the disposable-CI guard. These are fixed standard runner-preparation targets; there is no new purge of Go/Rust/SDK/native build caches. The first actual two-job run passed producer build/export, source/define/canonical matching and consumer import. Consumer space measured14GB free on the fresh VM,24GB after this standard cleanup,21GB after metadata/APK preparation and17GB after the approved image installation. The compile/image disk competition was resolved in that run; it then failed before App installation at emulator process-image ownership, not disk capacity.

`prepare` binds a new nonce, current job/SHA/workspace, source hashes, build mode and example canonical version to private SAFE_MODE=true/APP_ENV=dev defines. Add `--build-mode profile` to both prepare commands for the Profile control; the dedicated workflow already passes its mode input to both jobs. `install-tools` invokes only the existing official sdkmanager for `emulator` and the one fixed system image, validates API/ABI and saves hashes. `build` invokes the real `flutter build apk --<mode> --target-platform android-x64` itself, checks fresh output, exact mode-specific package/build/launcher/debug metadata, JIT/AOT payload and the actual x86_64 ELF architecture of Flutter and Core. Profile remains debuggable for the bounded authenticated VM observations. No alternate test entrypoint is used. The build output remains in private Actions logs for compiler diagnosis; it is not an artifact. Finite `apk-metadata.json` is written before acceptance validation so an identity refusal retains the actual mode and recognized metadata.

The first real CI run installed the official tools/image successfully, then exhausted runner disk during compilation; the runner itself could no longer write its diagnostic log. The second run compiled/staged the real APK successfully before installing the image, but still failed at image installation:72GB runner volume,3.0GB free after compilation and5.3GB after project `flutter clean`. The image phase reported `storage`. This is a measured disk-capacity failure, not a compiler diagnostic. The two fresh jobs replace that single-job strategy; no further global-cache purge, second image or paid runner is part of the change.

After all producer fresh-build checks, `build` exclusively copies the exact APK into fixed owned `private/app-<mode>.apk` and compares source/destination hashes. Its private receipt remains bound to the producer's job and nonce. `export` accepts only that locally compiled origin and creates a new directory containing exactly the mode-specific APK and `build-receipt.json`. The schema2 public receipt contains same repository/run/attempt/SHA, fixed producer job, source/define hashes, build mode, canonical example version/build/package/target, APK hash/size, actual build time and finite completed-build checks. It excludes the producer nonce, absolute paths, private state, define values, seeds, AVD, logs and VM service data. This is a consistency/provenance receipt for the trusted reviewed Actions pipeline, not a new cryptographic release-signing document. The workflow uploads producer diagnostics separately as `android-safe-build-receipts`, including on a validation failure.

`import` permits only the consumer role, exactly those two regular nonsymlinked incoming files, a bounded strict receipt schema, and a matching immutable dependency artifact ID. Receipt repository/run/attempt/SHA/producer, current source and canonical define hashes, example identity, completed build checks and APK size/hash must match; the actual x86_64 runtime ELF check runs again. The consumer then copies the APK into its own fixed private path and writes a **new local receipt bound to its current job and fresh nonce**. Imported origin is explicit, with the real producer build time and a separate local staging time; it never pretends the consumer compiled the App. The original producer private state/receipt cannot be reused directly in the consumer. `install-tools` and `run` revalidate this new local binding and the transfer provenance. Any mismatch blocks image installation/App startup. Source/define mismatches must be diagnosed, not waived. Reruns must rerun both jobs in the same attempt; an old producer artifact from another attempt is intentionally refused.

Android's Gradle root maps module output to project `build/`; Core AAR/classes/JNI are under `build/core/`. The locked Rust builder places Cargo target files below `.dart_tool/hooks_runner/`. Cleaning these project trees in the second run reclaimed only about2.3GB, leaving the compile toolchains/caches and image competing for the same volume. The consumer now carries only the checkout, metadata SDK/dependencies, approved image and staged APK. Producer and consumer `df` plus scoped `du` are the next-run evidence of that separation. The two-job run is not declared successful until it actually compiles, transfers, installs and renders there.

Flutter build stdout/stderr stream directly to the Actions job so a compiler failure retains its actual diagnostic. Runtime emulator/ADB/logcat output never uses that stream. A failed SDK manager returns only its bounded phase, numeric exit code and a finite storage/license/package/permissions/network/unknown classification; raw SDK output or URLs are not returned.

`run` rechecks the job, input and APK hashes, creates one private AVD under this project's `out/`, and launches a private ADB server on a fresh loopback port. It refuses occupied emulator ports 5554/5555 and accepts only an initially empty server and the exact sole `emulator-5554` serial after launch. Before installation/App launch and guest cleanup, `emu avd name` must identify this run's nonce-named AVD; matching API/ABI/serial alone grants no guest-cleanup permission. Emulator and ADB cleanup require the recorded PID, Linux start tick and SDK executable identity; there is no kill-by-name or other-device command. KVM is required, with headless `-gpu swiftshader`, no snapshot/audio/camera, and bounded subprocess/boot/UI waits. The worker may grant access to `/dev/kvm` on this disposable runner; no emulator runs on the workstation.

The official launcher parses `-no-window` as headless, maps x86_64 guests to the x86_64 backend, selects `qemu/linux-x86_64/qemu-system-x86_64-headless` and calls `safe_execv` on that engine. Both the public [35.3 release launcher](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-35-3-release/android/emulator/main-emulator.cpp) and [emulator development launcher](https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android/emulator/main-emulator.cpp) expose this layout. The previous failed run did not record its actual executable name, so that run cannot retrospectively prove which image was running.

Image acceptance is now narrower than the old under-SDK/basename condition: only the three complete known paths `emulator/emulator`, `emulator/qemu/linux-x86_64/qemu-system-x86_64` and `emulator/qemu/linux-x86_64/qemu-system-x86_64-headless` relative to the SDK can qualify. Existing candidates must be regular nonsymlinked files. Their SHA256 values are recorded after installation and checked again before launch; absent candidates remain absent. Runtime exec transitions must keep the actual Popen PID, kernel start tick and Python parent PID, with the currently observed exact candidate path/hash revalidated. `/proc` birth fields are read before and after resolving the executable; an inconsistent snapshot is refused. Same basename at another SDK path, changed file, parent change, PID reuse or unknown image cannot grant guest or signal authority. Escalated cleanup checks the current same-birth candidate hash before both terminate and kill.

`emulator-images.json` records only the bounded SDK package revision, fixed candidate classes/hashes/presence and prelaunch comparison. `result.json` records a finite observed basename/class, identity/hash booleans, seen-class list and `boot_completed_observed`, assigned before an identity requirement can fail. On failure, a separate `emulator_identity_at_failure` snapshot preserves that observation before cleanup can update the latest identity. Unknown names and paths stay out of diagnostics, and raw emulator/ADB output stays private. These fields make a future failure reviewable without accepting an unrecognized binary or exposing VM service data. Offline identity tests use synthetic files/process snapshots; they do not establish the actual next SDK boot or App result.

After real installation, the installed `base.apk` SHA must match the fresh build. The test completes the ordinary English disclaimer through its real Agree/restatement/Confirm UI, then checks the branded Chinese login form and submits empty fields to exercise local validation without an authentication request. The public restatement is typed in eight-character chunks, with the sole owned focused field checked against the exact expected prefix before and after every chunk. Existing, divergent or stalled input is refused; no preference, consent predicate or App text is bypassed. IME Back is sent only when the observed keyboard state is explicitly visible. It captures login, empty-field errors and reopened login as real native PNGs plus Android UI hierarchies. Home/reopen must retain the same App process. Back/reopen must return to login. The additional Activity and explicit-Quit gates are described below. **Active VPN, Doze, real login/commerce, update installation and the PackageInstaller confirmation flow remain outside this smoke.** Those require their own matching acceptance steps.

The next normal-main smoke adds `android_lifecycle_probe.py`; its source and the actual managed engine/lifecycle/Quit entry sources participate in the producer/consumer hash map. Other packages, traversal, extra lines and noncanonical encoding are refused. Installed bytes must still equal the staged APK hash. The earlier failed run did not preserve its raw path, so its precise string is unknown.

After ordinary consent/form/Home/Back checks, two `NEW_TASK|CLEAR_TASK` launches must produce real owned-client create/resume/destroy events and a different server Activity record while guest PID/start, VM pid/start and main isolate identity stay unchanged. Client lifecycle events are read only for the owned App PID, without clearing the shared event buffer. A server destroy request, Home, Back or same host emulator PID cannot satisfy this gate. Only authenticated loopback `getVM` is read through one freshly owned ADB forward; no evaluation, invocation, pause, VM extension, DevFS write or disabled authentication is used.

The driver then scrolls/reobserves the actual visible `退出客户端` button, captures its on-screen bounds and clicks it. Real client destruction plus absence of own Activities is required. A closed VM endpoint is recorded as unavailable, never as isolate-death proof. On ordinary reopen, the same guest process must expose an actually different main identity or VM instance, with the old isolate identity absent in that namespace. Finite `lifecycle.json` records these observation times separately. The exact owned forward is verified before removal; uncertain cleanup keeps the run red. URI/auth tokens, full VM responses, logcat/dumpsys and guest process details remain private.

These gates test SAFE stopped-state UI/isolate continuity, terminal Quit and healthy reopen. They do not count Java engine objects, establish sustained zero-View lifetime or activate VPN/Doze. `background_engine_verified` and `vpn_or_doze_tested` remain false. Actual runtime results and PNG inspection are still required; offline lifecycle fixtures do not establish those OS outcomes. Guest network fingerprints are also checked during guarded cleanup when earlier steps fail.
